relay-clidashboard mockups

Five ways to answer the three questions the current page cannot: what is each agent actually working on, what is it costing, and who handed work to whom. All five keep the existing palette, the existing type and the read-only rule — nothing here starts, stops or pauses anything. One invented fleet at one moment, 22:09:14, is drawn across all five so they can be compared. Each frame names the fields it reads today and the ones that need new plumbing.

Option A

Fleet board

The smallest change with the largest payoff: the sidebar card grows into a row that says what the agent is doing, how far into its budget it is, and how hard it is working. Money and tokens stop being a single running total and become a meter against the ceiling the config already sets.

Answers
Which agent is on which task, how close a run is to max_usd_per_run, how much of the token spend was cache, and whether work is sitting unclaimed.
Reads today
runs_last_hour, max_runs_per_hour, cost_usd, usage.cached_input, num_turns, tool_calls, next_poll_at, the live tool_use stream.
Needs plumbing
A task_id on RunSummary, captured from the relay:claim_task call the run already makes. A fleet rollup in Snapshot. Per-worker hourly buckets for the sparkline (client-side from runs).

Option B

Handshake timeline

One lane per worker on a shared clock. A run is a bar, its tool calls are the ticks inside it, and the arrows are the handshakes: the moment an orchestrator spawned a subtask and the moment the agent that took it woke the orchestrator back up. The fourth lane is work Relay is holding that no worker has claimed, which today is a number in a poll line and nothing more.

Answers
Who handed what to whom, how long each hop took, where the fan-out went wide, and what has been sitting unclaimed while the fleet was busy elsewhere.
Reads today
Every bar: RunSummary.started_at/ended_at, outcome, cost_usd, usage, num_turns. Every tick: a session event of type tool_use. Bus.History already interleaves all workers by sequence.
Needs plumbing
The arrows: parent and child ids from the task_id= and subtask_id= targets toolTarget already extracts, joined across workers. The unclaimed lane needs the ids behind todo_total, which the probe does not ask for — attention_ids is the precedent.

Option C

Fan-out view

The timeline answers “when”; this answers “what came from what”. One held task at the root, the subtasks it spawned beneath it, each carrying the agent that took it and what it has cost so far — and a rolled-up figure at the root, which is the number worth knowing before an orchestrator fans out again. Underneath, the handshakes as a plain list, which is often all anyone needs.

Answers
What did this one instruction actually cost, end to end, across every agent it pulled in? Which branch is stalled? Which agent is doing the expensive part?
Reads today
Per-run cost, tokens, turns and outcome; the relay:create_task and relay:claim_task calls with their targets; attention_ids, which is already how a parent learns a child moved.
Needs plumbing
Task titles — visible only when an agent passes title= or description= to a tool call. A parent/child map held per fleet run, and a rollup that adds claude dollars and codex tokens without mixing them.

Option D

Run inspector

The current feed is the right thing to watch and the wrong thing to read: everything streams past at the same weight. Here the narration keeps the whole width it has now, and a rail holds the numbers that only make sense against a ceiling — dollars against the per-run cap, seconds against the timeout, and the cache share that explains why a long run can still be cheap.

Answers
Is this run about to hit a cap? Is it working or looping? Where did the money go — more turns, or bigger ones?
Reads today
All of it, except the histogram grouping: cost_usd, usage.input/cached_input/output, num_turns, tool_calls, max_usd_per_run, max_seconds_per_run, and the tool_use events themselves.
Needs plumbing
Counting tools by name, and the gap between consecutive events. Both are client-side arithmetic over events the page already holds in its ring.

Option E

Spend ledger

A fourth sidebar entry next to Configuration, for the question asked after the fleet has been running a while rather than during. Cost per run and per turn, the outcome mix, the cache share, and where the hour went. The two runtimes stay in their own units: claude reports dollars, codex reports tokens, and nothing here converts one into the other.

Answers
What did the last hour cost, which worker or model is expensive, how much of the spend went to runs that timed out, and is the cache doing its job?
Reads today
Entirely WorkerStatus.runs, which already carries cost_usd, usage, num_turns, tool_calls, outcome and both timestamps for every retained run.
Needs plumbing
Nothing on the wire for the table or the chart. The per-task column needs the same task_id on RunSummary that A, B and C want; it is the one new field all four share.
